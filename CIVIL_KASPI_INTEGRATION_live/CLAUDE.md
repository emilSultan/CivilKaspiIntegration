# CLAUDE.md

Этот файл — памятка для Claude Code при работе с этим репозиторием.

## Что это

`Ext/ObjectModule.bsl` — модуль объекта внешней обработки 1С (ВнешняяОбработка), зарегистрированной под
идентификатором `KASPI_BACKGROUND_TASKS` (см. `СведенияОВнешнейОбработке()`). Она выполняет фоновую синхронизацию
между Order API Kaspi.kz (`https://kaspi.kz/shop/api/v2/*`) и этой базой "1С:Розница": забирает новые заказы,
подтверждает их, проверяет статус доставки/завершения, создаёт документы `РеализацияТоваров`, отправляет остатки.
Это отдельная обработка, никак не связанная с `KASPI_CARDS_RT` и `Kaspi/CivilKaspiCards_14.08_for_claude`
(интеграции карточек товаров/классификатора) и с `ЗагрузитьМеппингКаспи` (вспомогательная обработка для маппинга
категорий) из этого же репозитория — **не переноси сюда auth/HTTP-логику оттуда**, она здесь другая (см. раздел
про авторизацию ниже).

## Сборка / линт / тесты

Их нет, локально. Как и в `Kaspi/CLAUDE.md`: код редактируется здесь как обычный текст, а изменения потом вручную
переносятся в реальный `.epf` через Конфигуратор (подтверждено пользователем — этот проект **не** синхронизирован
через 1С:EDT, поэтому правка одного этого файла сама по себе ничего не меняет в том, что открывает Конфигуратор).
Прогнать или протестировать этот код из шелла нельзя.

**Синтаксическая ловушка 1С, на которую наткнулись в этой сессии:** внутри `Функция` голый `Возврат;` без
выражения — синтаксическая ошибка (`Ожидается выражение`) — 1С требует `Возврат <значение>;` (например,
`Возврат Неопределено;`), если текущий блок — `Функция`. Голый `Возврат;` работает только внутри `Процедура`.
В нескольких функциях этого файла (`РеализацияТоваров`, `СоздатьЗаказ`, `Подтвердить_ЗаказКаспи2`, ...) есть
ранние выходы по условию — перед тем как добавлять новый, всегда проверяй, `Функция` это или `Процедура`.

## Точки входа

`ВыполнитьКоманду(ИмяКоманды)` диспетчеризует по имени. Зарегистрированные команды (`СведенияОВнешнейОбработке`):

| Команда | Назначение |
|---|---|
| `GET_ORDERS` | Опрашивает `v2/orders?...state=NEW` за скользящее окно 3 дня и создаёт/подтверждает документы `ЗаказПокупателя`. |
| `UPDATE_BO_STORE_STOCK`, `UPDATE_KASPI_STOCK` | Отправка/получение остатков между базой и Kaspi. |
| `GET_STATUS_DELIVERY` | Опрос статуса доставки. |
| `GET_STATUS_COMPLETED` | Находит закрытые `ЗаказПокупателя` без `РеализацияТоваров` и создаёт её (см. исправленный баг ниже). |
| `GET_CANCELLED_ORDERS` | Опрашивает статус `ARCHIVE` и помечает соответствующие локальные заказы отменёнными. |
| `SEND_NEW_ORDERS` | (см. `PostMail` в модуле формы). |

Модуль формы (`Forms/Форма/Ext/Form/Module.bsl`) подключает кнопками только `UPDATE_BO_STORE_STOCK`,
`UPDATE_KASPI_STOCK`, `get_delivery` (→ `GET_STATUS_DELIVERY`) и `PostMail` (→ `SEND_NEW_ORDERS`) — `GET_ORDERS`,
`GET_STATUS_COMPLETED`, `GET_CANCELLED_ORDERS`, judging по всему, запускаются по расписанию через подсистему
`ДополнительныеОтчетыИОбработки`, а не из этой формы.

## Авторизация / HTTP-запросы — подтверждено в проде, не "чинить"

- `X-Auth-Token` **захардкожен** в `ПолучитьЗаголовкиЗапросаHTTP()`: `cE0P0Z2VJQGvrE0g5oYccTNHmrwyV7vIJiheNP5ugVU=`.
  Это реальный, действующий продовый токен — не заменяй его на динамическое получение (например, из
  `ИнтернетМагазины.ДополнительныеПараметры`) без согласования с пользователем. В одной из прошлых итераций такой
  же захардкоженный токен в *другой* Kaspi-обработке ошибочно посчитали устаревшим и заменили на динамический
  поиск, который на деле оказался не заполнен — это молча сломало все запросы к Kaspi в той обработке.
- `X-Merchant-Uid` в этом файле **вообще не используется**. Для этих эндпоинтов достаточно `X-Auth-Token`.
- HTTP-запросы идут через общий модуль `КоннекторHTTP.GetJson(АдресРесурса, Неопределено, Структура("Заголовки"[,"Таймаут"], ...))`
  — это реальный общий модуль в этой конфигурации, доступный из любой внешней обработки. Всегда предпочитай его
  вместо ручной сборки `HTTPЗапрос`/`HTTPСоединение`; смотри `КоннекторHTTP\.` по всему файлу для других вариантов
  вызова (`GetJson`, `PostJsonGetHTTPResponse`, `КакТекст`).
- Ссылка на магазин Kaspi — `kaspi()` → делегирует в общий модуль
  `ИнтеграцияWB.ИнтернетМагазинПолучитьДопПараметру("Kaspi")`, что эквивалентно
  `Справочники.ИнтернетМагазины.НайтиПоКоду("000000001")` (в паре мест этого же файла используется и напрямую).

## Захардкоженный маппинг пунктов выдачи

`ПолучитьТочкиПродаж(АдресРесурса, ЭтоКаспиДоставка, НомерЗаказа)` сопоставляет `deliveryPointOfService.displayName`
из Kaspi со складом:

- `"PP1"` → `Справочники.Склады` с `КодИсточника = "M07901"`
- `"PP2"` → `Справочники.Склады` с `КодИсточника = "AW02"`
- всё остальное → `Склад = Неопределено`, и **с этой сессии** это пишется в журнал
  `РегистрыСведений.ИнтеграцияЖурналПроцессов` (через `ЗаписатьВЖурналРегистра`, источник `"GET_ORDERS"`), а не
  тонет молча, как раньше.

Подтверждено пользователем (2026-09-23): это единственные два пункта выдачи. Если появится третий, теперь он
попадёт в журнал с неопознанным кодом — в этом случае нужно расширить цепочку `Если/ИначеЕсли`, а не добавлять
третью тихую ветку.

## Баги, исправленные в этой сессии

1. **Создавались и проводились пустые документы `РеализацияТоваров`.** `GET_STATUS_COMPLETED` → `РеализацияТоваров()`
   вызывала `СоздатьРеализацию()` безусловно; этот хелпер создаёт *и сразу проводит* документ `РеализацияТоваров`
   до того, как в него добавлены товары. Если запрос по строкам заказа (`Рез`) возвращал ноль строк, документ всё
   равно создавался, проводился и оставался пустым. Исправлено добавлением
   `Если Рез.Количество() = 0 Тогда Возврат Неопределено; КонецЕсли;` **до** вызова `СоздатьРеализацию()`, чтобы
   документ вообще не создавался, если нечего продавать. (У соседней функции `Перемещение_Товаров_И_Реализация_Товаров`
   такая проверка уже была — код в этом файле местами защищённый, местами нет, не полагайся на единообразие.)

2. **Заказы иногда тихо не создавались** (`GET_ORDERS` → `СоздатьЗаказ` → `ПолучитьorderOrderEntries`). Два места
   поиска возвращали `Неопределено` **без единой записи в журнал**, обрывая весь заказ без следа:
   - `ПолучитьТоварыЗаказа`: штрихкод товара из Kaspi не найден в `РегистрСведений.Штрихкоды`.
   - `ПолучитьТочкиПродаж`: код пункта выдачи, отличный от `PP1`/`PP2` (см. выше).

   Теперь оба места вызывают `ЗаписатьВЖурналРегистра(ПолучитьПараметрИсточника("GET_ORDERS"), НомерЗаказа, Ложь, "...")`
   с проблемным значением (штрихкод / код пункта выдачи) в тексте сообщения — так что будущие пропажи можно будет
   диагностировать по журналу, а не просто гадать "заказ куда-то делся".

**Не исследовано / отмечено, но не исправлено:** заказы, у которых атрибут `state` от Kaspi равен `"SIGN_REQUIRED"`,
пропускаются при каждом опросе (`ОбработатьЗаказы`, обе ветки — и создание, и подтверждение) без какого-либо
отслеживания. Если Kaspi отменит такой заказ по таймауту до того, как он выйдет из `SIGN_REQUIRED`, он никогда не
попадёт в базу — и, в отличие от двух случаев выше, здесь по-прежнему нет логирования. Возможно, это ожидаемое
поведение (отменённый до подписи заказ, наверное, и не должен создаваться), но если жалобы на "пропавшие заказы"
продолжатся — стоит обсудить с пользователем отдельно.
