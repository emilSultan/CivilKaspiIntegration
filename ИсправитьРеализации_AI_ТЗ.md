# Техническое задание для AI: доработка обработки «ИсправитьРеализации»

## Цель

Доработать существующую обработку **`ИсправитьРеализации`**. Обработка должна принимать список номеров заказов, проверять наличие этих заказов в проведённых документах реализации за указанный месяц и при необходимости переносить либо создавать реализации на дату, заданную пользователем.

## Обязательный источник структуры метаданных

Структуру конфигурации, документов, реквизитов и табличных частей необходимо определять по файлу **`civil_retail.json`**.

- Перед изменением кода изучить в `civil_retail.json` структуру обработки `ИсправитьРеализации`, документов **«Заказ покупателя»** и **«Реализация товаров»**.
- Использовать точные технические имена объектов, реквизитов и табличных частей из `civil_retail.json`.
- Не придумывать имена метаданных.
- Указанные в этом задании русские названия документов могут быть пользовательскими представлениями. В коде использовать имена, подтверждённые файлом `civil_retail.json`.
- В частности, проверить точные имена реквизитов `НомерЗаказаНаСайте`, `НомерЗаказа`, табличной части `Товары` и всех полей, необходимых для заполнения реализации.

## Изменения формы обработки

В существующую форму обработки добавить:

1. **ТабличныйДокумент** для вставки списка номеров заказов.
   - Пользователь должен иметь возможность скопировать номера из Excel и вставить их в ТабличныйДокумент.
   - Один номер заказа должен считываться как одно отдельное значение.
   - Пустые строки и пустые ячейки необходимо пропускать.
   - Повторяющиеся номера в рамках одного запуска не нужно обрабатывать повторно.
2. Реквизит формы **`Дата`**.
   - Месяц и год этой даты определяют требуемый период.
   - Эта же дата устанавливается во всех новых документах реализации, создаваемых обработкой.
3. Команду и кнопку **«Исправить реализации»**.
   - Нажатие кнопки запускает обработку всех номеров из ТабличногоДокумента.

## Основные определения

- Заказ считается находящимся в требуемом периоде, если **месяц и год даты проведённой реализации** совпадают с месяцем и годом реквизита `Дата` на форме.
- Поиск номера заказа в реализации выполнять в табличной части **`Товары`** по реквизиту **`НомерЗаказа`** с использованием точных технических имён из `civil_retail.json`.
- Учитывать только **проведённые** документы реализации.
- Проверка статуса заказа `Completed` не требуется.

## Алгоритм обработки

Для каждого уникального непустого номера заказа из ТабличногоДокумента выполнить следующие действия.

### 1. Поиск реализации в требуемом периоде

Найти проведённые реализации, в табличной части `Товары` которых присутствуют строки с текущим `НомерЗаказа`.

Если хотя бы одна такая проведённая реализация относится к месяцу и году, указанным пользователем:

- ничего не изменять;
- перейти к следующему номеру заказа.

### 2. Заказ найден только в реализации другого периода

Если строки текущего заказа найдены в проведённой реализации, но не в требуемом месяце и году:

1. Создать новый документ **«Реализация товаров»**.
2. Установить дату нового документа равной значению реквизита `Дата` на форме.
3. Перенести в новый документ данные и строки, относящиеся **только к текущему номеру заказа**.
4. Заполнить обязательные реквизиты документа на основании исходной реализации и структуры метаданных из `civil_retail.json`.
5. Записать и провести новую реализацию.
6. Только после успешного проведения новой реализации удалить из исходной реализации строки табличной части `Товары`, у которых `НомерЗаказа` равен текущему номеру.
7. Записать и перепровести исходную реализацию.

Нельзя удалять исходную реализацию целиком, если в ней находятся другие заказы. Из неё удаляются только строки текущего заказа.

### 3. Заказ не найден ни в одной проведённой реализации

Если текущий номер заказа не найден ни в одной проведённой реализации:

1. Найти документ **«Заказ покупателя»** по реквизиту **`НомерЗаказаНаСайте`**. Значение этого реквизита должно совпадать с номером из ТабличногоДокумента.
2. Поиск выполнять именно по `НомерЗаказаНаСайте`, а не по стандартному номеру документа.
3. Взять из найденного заказа данные, необходимые для создания реализации.
4. Создать новый документ **«Реализация товаров»**.
5. Установить дату документа равной значению реквизита `Дата` на форме.
6. Заполнить шапку и табличные части по данным найденного заказа с учётом структуры `civil_retail.json` и применяемой в конфигурации стандартной логики создания реализации на основании заказа.
   - **Исключение:** реквизиты `Склад` и `Магазин` **не берутся из заказа** — у заказов покупателя встречаются разные и некорректные склады. Вместо этого `Склад`/`Магазин` берутся из любой проведённой реализации в базе (первая попавшаяся, реквизиты одинаковы для всех проведённых реализаций).
7. Записать и провести новую реализацию.

Если документ «Заказ покупателя» по `НомерЗаказаНаСайте` не найден, не создавать пустую реализацию: зафиксировать ошибку по этому номеру и продолжить обработку остальных заказов.

## Требования к безопасному изменению данных

- Не менять реализации, в которых заказ уже находится в требуемом периоде.
- Не удалять строки из старой реализации до успешной записи и проведения новой реализации.
- При ошибке создания или проведения новой реализации исходную реализацию не изменять.
- Из старого документа удалять только строки с обрабатываемым `НомерЗаказа`.
- После удаления строк исходный документ необходимо записать и провести повторно.
- Если перепроведение исходной реализации завершается ошибкой, обработать ошибку и не скрывать её от пользователя.
- Ошибка по одному заказу не должна прекращать обработку всего списка: перейти к следующему номеру.
- Не отключать проверки и стандартные механизмы проведения конфигурации без необходимости.

## Результат выполнения

После завершения вывести пользователю итог по каждому номеру заказа. Достаточно следующих результатов:

- уже находится в требуемом периоде — пропущен;
- перенесён из реализации другого периода;
- создана реализация по заказу покупателя;
- заказ покупателя не найден;
- ошибка создания или проведения новой реализации;
- ошибка изменения или перепроведения исходной реализации.

Итоговое сообщение должно также содержать общее количество успешно обработанных, пропущенных и ошибочных заказов.

## Ожидаемый результат доработки

AI должен изменить существующую обработку **`ИсправитьРеализации`**, включая форму и программные модули, а не создавать отдельную новую обработку. Код должен компилироваться и использовать только реально существующие объекты и реквизиты, подтверждённые в `civil_retail.json`.

## Статус реализации

Доработка выполнена в `ИсправитьРеализации/Forms/Форма/Ext/Form.xml` и `.../Form/Module.bsl` (обработка изначально была пустым шаблоном без формы и без кода - всё написано с нуля). Уточнения и решения, принятые в ходе разработки:

- **Чтение номеров из ТабличногоДокумента**: считываются все непустые ячейки (все строки и столбцы, а не только первый столбец), с обрезкой пробелов и дедупликацией в рамках одного запуска.
- **Заполнение шапки/строк новой реализации** (и в сценарии 2, и в сценарии 3) сделано не через платформенный механизм «Ввод на основании» (`Заполнить()`), а через `ЗаполнитьЗначенияСвойств` по образцу уже рабочего кода `CIVIL_KASPI_INTEGRATION_live.СоздатьДокРеализациюТоваров` из этого же репозитория - это единственный подтверждённо рабочий в данной конфигурации способ создать реализацию из заказа/другой реализации.
- **Склад и Магазин для сценария 3** берутся не из заказа, а из любой проведённой реализации в базе (см. правку в разделе выше) - это отдельное уточнение, полученное после первой версии реализации.
- **Опустевшая исходная реализация** (сценарий 2, если после удаления строк текущего заказа в документе не осталось никаких строк): документ не удаляется (запрещено ТЗ) и не остаётся пустым проведённым (это отдельно найденный и исправленный в этой сессии баг в `CIVIL_KASPI_INTEGRATION_live`) - вместо этого он распроводится (`Проведен = Ложь`) и сохраняется.
- **Результат по каждому заказу** выводится построчно в отдельный табличный документ `ТабДокРезультатРеализаций` (колонки: номер заказа / результат / комментарий), плюс итоговая сводка счётчиков через `Сообщить()`.
- Обработка синхронизируется с 1С только вручную через Конфигуратор (как и остальные обработки в этом репозитории) - изменения в этих файлах нужно перенести в реальную `.epf` руками.

## Расширение: возвраты товаров от покупателя

По тому же принципу и на тех же данных формы (`ТабДок` с номерами заказов, `Дата`) добавлена вторая кнопка/команда **«Исправить возвраты»**, работающая с документом **«Возврат товаров от покупателя»** (техническое имя `Документ.ВозвратТоваровОтПокупателя`, подтверждено `civil_retail.json`) — у него тоже есть реквизит `НомерЗаказа` в табличной части `Товары`.

Алгоритм для каждого номера заказа - полный аналог алгоритма для реализаций, с заменой документа:

1. **Поиск возврата в требуемом периоде.** Найти проведённые возвраты, в `Товары` которых есть строки с текущим `НомерЗаказа`. Если хотя бы один такой возврат относится к месяцу и году `Дата` - ничего не менять, перейти к следующему номеру.
2. **Номер найден только в возврате другого периода.** Создать новый возврат, датировать `Дата`, перенести в него только строки текущего `НомерЗаказа` (шапка копируется с исходного возврата тем же приёмом `ЗаполнитьЗначенияСвойств`, что и для реализаций). Только после успешного проведения нового возврата - удалить перенесённые строки из исходного и перепровести его. Исходный документ целиком не удаляется никогда; если после удаления строк в нём не осталось ни одной строки - он распроводится (`Проведен = Ложь`), а не остаётся пустым проведённым.
3. **Номер не найден ни в одном проведённом возврате.** Создать новый возврат **на основании проведённой «Реализации товаров»** с этим `НомерЗаказа` (не на основании заказа покупателя):
   - найти проведённую `Документ.РеализацияТоваров`, в `Товары` которой есть строки с этим `НомерЗаказа`;
   - если реализация не найдена - зафиксировать ошибку по этому номеру, возврат не создавать, продолжить со следующим номером;
   - если найдена - создать `Документ.ВозвратТоваровОтПокупателя`, заполнить шапку из реализации (`ЗаполнитьЗначенияСвойств`), явно проставить `ДокументОснование = Реализация` и обязательный `АналитикаХозяйственнойОперации = Справочники.АналитикаХозяйственныхОпераций.ВозвратТоваровОтПокупателя` (этого реквизита нет в реализации, взять неоткуда, кроме как проставить предопределённым значением явно), перенести только строки текущего `НомерЗаказа` с проставлением `ДокументПродажи = Реализация` по каждой строке, дата документа = `Дата` формы, записать и провести.
   - Источник и точный приём копирования подтверждены рабочим кодом `CIVIL_KASPI_INTEGRATION_live.ВозвратЗаказа` из этого репозитория.

Требования к безопасному изменению данных, набор итоговых статусов и правило «не отключать стандартные проверки» действуют так же, как для реализаций (раздел «Требования к безопасному изменению данных» выше), с поправкой на терминологию:

- уже находится в требуемом периоде — пропущен;
- перенесён из возврата другого периода;
- создан возврат по реализации товаров;
- реализация товаров не найдена — возврат не создан;
- ошибка создания или проведения нового возврата;
- ошибка изменения или перепроведения исходного возврата.

Результат по каждому заказу выводится построчно в отдельный табличный документ `ТабДокРезультатВозвратов` (не путать с `ТабДокРезультатРеализаций` кнопки «Исправить реализации» - у каждой кнопки свой вывод, чтобы не затирать результат другой), плюс отдельная итоговая сводка через `Сообщить()`. Реализация: `ИсправитьРеализации/Forms/Форма/Ext/Form/Module.bsl`, регион `#Область Возвраты`.

## Расширение: сравнительный отчёт по суммам

Третья кнопка/команда **«Сравнить суммы»**. Пользователь вставляет строки «номер заказа - сумма» (два столбца: 1 - номер заказа, 2 - сумма, без заголовка) в отдельный табличный документ `ТабДокСравнение`, указывает `Дата` (месяц/год - тот же реквизит, что и для реализаций/возвратов) и запускает сравнение с базой.

Номера заказов в присланном списке **могут повторяться** (например, несколько товарных строк одного заказа) - такие строки не сравниваются с базой по отдельности, а сначала **суммируются по номеру заказа**, отдельно сумма всех строк с суммой > 0 и отдельно сумма всех строк с суммой ≤ 0 (у одного и того же номера заказа может быть и продажа, и возврат - они складываются в разные накопители и далее сравниваются с базой независимо друг от друга).

Для каждого номера заказа (после группировки и суммирования):

1. Сумма считывается через `Число()` (запятая заменяется на точку, пробелы и неразрывные пробелы убираются). Если хотя бы одна строка не распознана - эта строка попадает в результат отдельно, со статусом «Не удалось прочитать сумму» (не участвует в суммировании, но не прерывает обработку остальных строк с тем же номером).
2. Накопленная сумма всех строк этого номера **больше нуля** - сравнивается с суммой строк `Документ.РеализацияТоваров.Товары.Сумма` по всем **проведённым** реализациям за месяц/год `Дата` с этим `НомерЗаказа` (суммируется по всем документам, если заказ разбит на несколько).
3. Накопленная сумма всех строк этого номера **меньше или равна нулю** - сравнивается с суммой строк `Документ.ВозвратТоваровОтПокупателя.Товары.Сумма` по проведённым возвратам за тот же период с этим `НомерЗаказа`, взятой **со знаком минус** (в базе возврат хранится положительным числом). Если по одному номеру присланы и положительные, и неположительные строки - в отчёт может попасть до двух строк по этому номеру (одна - сравнение с реализацией, другая - с возвратом).
4. Если в базе по номеру (и по этому источнику) ничего не найдено - сумма базы считается 0.
5. Разница = накопленная введённая сумма − сумма базы, округляется до 2 знаков. **В результат попадают только строки, где разница не равна нулю** - если совпало, заказ (по этому источнику) в отчёт не выводится.

**Заказы из базы, не присланные пользователем.** Помимо сравнения присланных пар, отчёт дополнительно находит все `НомерЗаказа` (непустые), встречающиеся в проведённых `РеализацияТоваров`/`ВозвратТоваровОтПокупателя` за месяц/год `Дата`, но отсутствующие среди присланных в `ТабДокСравнение` номеров - и добавляет их в тот же результат:

- источник - `Реализация товаров` или `Возврат товаров от покупателя` (если номер встретился в обоих - две отдельные строки);
- колонка «Введённая сумма» = `не прислан`;
- колонка «Сумма в базе» и «Разница» заполняются по той же знаковой логике, что и для присланных пар (для возврата - сумма базы со знаком минус);
- отчёт строится даже если пользователь вообще не прислал ни одной пары (пустой `ТабДокСравнение`) - в этом случае будут показаны все заказы периода из базы.

Колонки результата (`ТабДокСравнениеРезультат`): номер заказа, источник (реализация/возврат), введённая сумма, сумма в базе, разница. В конце - сводка через `Сообщить()`: сколько пар проверено, сколько с расхождением, сколько с ошибкой чтения суммы, сколько найдено в базе, но не прислано. Реализация: `ИсправитьРеализации/Forms/Форма/Ext/Form/Module.bsl`, регион `#Область СравнениеСумм` (функции `СуммыРеализацийЗаПериодНаСервере` / `СуммыВозвратовЗаПериодНаСервере`).

### Исправленный баг: ложное «расхождений нет» при заказе с продажей и возвратом одновременно

Найдено и исправлено на реальных данных (`данныеизбазы.xlsx` / `изфайла.xlsx`, заказ `992265585`):
в файле по этому номеру присланы только строки продажи, а в базе за тот же период по этому же
номеру дополнительно есть проведённый возврат, которого в файле нет вовсе. Отчёт эту разницу не
показывал.

Причина: «присланность» номера заказа отслеживалась одним общим флагом (`ВведённыеНомера`) без
разделения по стороне (продажа/возврат). Из-за этого:
- в основном цикле сравнения сторона, по которой не прислали ни одной строки, пропускалась, т.к.
  проверялось `Группа.СуммаРеализации <> 0` / `Группа.СуммаВозврата <> 0`, а не факт присылки;
- в цикле «найдено в базе, но не прислано» заказ пропускался целиком, если хотя бы одна его
  сторона была прислана - даже если другая сторона в файле отсутствовала.

Исправление: заведены два отдельных флага/словаря присланности - `ВведённыеНомераРеализация` и
`ВведённыеНомераВозврат`, плюс `Группа.ЕстьРеализация`/`Группа.ЕстьВозврат` (ставятся по факту
получения хотя бы одной строки соответствующего знака, а не по итоговой ненулевой сумме). Каждая
сторона каждого номера заказа теперь сравнивается и/или попадает в «не прислано» независимо от
другой стороны того же номера.
